# openarcanum.org

This server runs the OpenArcanum website: the landing page with
announcements, the bug and security report forms, the security policy, and
the admin portal at `https://openarcanum.org/admin`. Keep this file at
/root/README.md on the server.

## What runs here, and as whom

- One container, `openarcanum-site`, from the image
  `ghcr.io/hyperkubeorg/openarcanum-site`. The program inside is `site`.
- It runs under rootless podman as the user `openarcanum`. That user has no
  password and no sudo. Root manages it.
- systemd starts it at boot. The unit is a systemd **user** unit of
  `openarcanum`, generated by Quadlet from a `.container` file. Lingering is
  on for the user, so its units start without anyone logging in.
- The container uses the host network. It listens on 443/tcp (HTTPS, with its
  own Let's Encrypt certificate) and on 7380/tcp for plain HTTP, which only
  redirects to https. firewalld forwards port 80 to 7380.
- Inside the container the program runs as uid 65532. On the host that uid is
  the user `openarcanum` (`UserNS=keep-id:uid=65532,gid=65532`). So every file
  it writes is owned by `openarcanum`.

Two helper commands, installed by setup.sh, run things as `openarcanum` from a
root shell:

```sh
oa-systemctl status openarcanum-site    # systemctl --user as openarcanum
oa-podman ps                            # podman as openarcanum
```

## Where everything lives

| Path | What |
|---|---|
| `/home/openarcanum/.config/containers/systemd/openarcanum-site.container` | Quadlet file: image tag, mounts, health check |
| `/home/openarcanum/.config/systemd/user/openarcanum-site-backup.{service,timer}` | daily backup job |
| `/home/openarcanum/site/config/site.json` | site config, mounted read-only at `/etc/openarcanum/site.json` |
| `/home/openarcanum/site/data/` | `site.db` (admins, sessions, announcements, reports); mounted at `/data` |
| `/home/openarcanum/site/data/backups/` | backups from `site backup` |
| `/home/openarcanum/site/keys/storage.key` | the key that seals reports, notes and two-factor secrets; mounted at `/keys` |
| `/home/openarcanum/site/acme/` | Let's Encrypt account key and certificates; mounted at `/acme` |
| `/home/openarcanum/.local/share/containers/` | podman's image store for the user |
| `/etc/sysctl.d/90-openarcanum.conf` | lets unprivileged processes bind port 443 |
| `/usr/local/sbin/oa-podman`, `/usr/local/sbin/oa-systemctl` | the helper commands |
| `/root/openarcanum-podman/` | the setup kit (a copy of `deploy/podman` from the repository) |

The kit in `/root/openarcanum-podman/openarcanum.org/` is the source of truth.
To change the config or the image tag, edit the files there and run `setup.sh`
again. It copies them into place and restarts the site only when something
changed. Edits made directly under `/home/openarcanum` are overwritten the
next time setup.sh runs.

## How it was set up

From a checkout of the repository on your own machine:

```sh
scp -r deploy/podman root@openarcanum.org:/root/openarcanum-podman
ssh root@openarcanum.org
bash /root/openarcanum-podman/openarcanum.org/setup.sh
```

Before that, the DNS A record (and AAAA, if the server has IPv6) for
`openarcanum.org` must point at this server.

The script stops at the first error and can be run again at any time. It does
this, in order:

1. Installs `podman`, `container-selinux`, `firewalld`, `chrony`, `curl`,
   `openssl` with dnf and checks podman is 4.9 or newer.
2. Enables chronyd and checks the clock is synchronized.
3. Creates the user `openarcanum`, checks it has 65536 subordinate uids and
   gids (`/etc/subuid`, `/etc/subgid`), and runs
   `loginctl enable-linger openarcanum`.
4. Writes `/etc/sysctl.d/90-openarcanum.conf` with
   `net.ipv4.ip_unprivileged_port_start = 443` and applies it.
5. Opens 443/tcp in firewalld and forwards port 80 to 7380 (permanent, then
   reload).
6. Creates `/home/openarcanum/site/{config,data,keys,acme}` owned by
   `openarcanum`, mode 0700 for data, keys and acme.
7. Installs `oa-podman` and `oa-systemctl`.
8. Copies `site.json`, the Quadlet file, the backup units and this README into
   place, and runs `restorecon` on `~openarcanum/.config`.
9. Runs the Quadlet generator in dry-run mode to catch mistakes.
10. Checks DNS, then pulls the image as `openarcanum`.
11. Runs `systemctl --user daemon-reload`, enables the backup timer and
    (re)starts `openarcanum-site`.
12. Checks: the unit is active, the container health check passes, a trusted
    certificate is served for the name, the home page is served, and the
    storage key exists. Then it lists the admin accounts and prints the
    commands below for creating the first one.

The site creates `storage.key` on its first start. Copy it somewhere safe off
this machine right away (a password manager, an encrypted USB stick). Backups
can't be read without it.

### The first admin

There is no sign-up. Create the admin yourself; it asks for a passphrase (at
least 12 characters) without echo:

```sh
oa-podman exec -it openarcanum-site site admin add NAME
oa-podman exec -it openarcanum-site site admin totp NAME
```

The second command prints a key and an `otpauth://` URI for an authenticator
app, and turns two-factor sign-in on once you type a current code. Then sign in
at `https://openarcanum.org/admin`.

## Start, stop, status, logs

```sh
oa-systemctl status openarcanum-site
oa-systemctl restart openarcanum-site
oa-systemctl stop openarcanum-site
oa-systemctl start openarcanum-site
```

`enable` and `disable` don't apply to Quadlet units. The `[Install]` section of
the `.container` file makes it start at boot. To keep it from starting at
boot, move the `.container` file out of the Quadlet directory and run
`oa-systemctl daemon-reload`.

Logs go to journald:

```sh
journalctl CONTAINER_NAME=openarcanum-site -f            # the site's log and access log
journalctl CONTAINER_NAME=openarcanum-site --since today
journalctl _SYSTEMD_USER_UNIT=openarcanum-site.service   # start/stop messages too
oa-podman healthcheck run openarcanum-site && echo healthy
```

The access log writes `-` for client addresses (`"log_client_ips": false`).
Report contents, passphrases and codes are never logged.

Health on the status listener (loopback only):

```sh
curl -s http://127.0.0.1:7301/healthz
```

## Updating to a new release, and rolling back

The image tag is pinned in the Quadlet file (`Image=...:2026.10.0`). Releases
are tagged `<version>` (for example `2026.10.1`), `YYYY.MM` and `latest`.

To upgrade:

```sh
# 1. Take a backup first. Rolling back needs it.
oa-podman exec openarcanum-site site backup -out /data/backups -keep 14
# 2. Change the tag in the kit.
cd /root/openarcanum-podman/openarcanum.org
sed -i 's|^Image=.*|Image=ghcr.io/hyperkubeorg/openarcanum-site:2026.10.1|' openarcanum-site.container
# 3. Pull, restart, check.
bash setup.sh
```

To roll back, put the old tag back the same way and run setup.sh. If the new
release changed the database schema, the old one refuses to start; then also
restore the backup taken before the upgrade (below).

### Automatic updates

The container carries the label `io.containers.autoupdate=registry`.
`podman auto-update` pulls the pinned tag again and restarts the site when the
tag points at a new image. With a version tag that only happens if a release is
republished. To follow fixes for the month automatically, set the tag to
`YYYY.MM` (for example `2026.10`).

The timer that runs it daily is off. To check or turn it on:

```sh
oa-podman auto-update --dry-run
oa-systemctl enable --now podman-auto-update.timer
oa-systemctl list-timers
```

If the new container fails to start, podman rolls back to the previous image.

## Backups and restore

What to keep:

| Path | Why |
|---|---|
| `/home/openarcanum/site/data/backups/site-backup-*.db` | consistent copies of the database, from `site backup` |
| `/home/openarcanum/site/keys/storage.key` | needed to read any backup. Keep it apart from the backups |
| `/home/openarcanum/site/acme/` | optional: saves asking Let's Encrypt again after a rebuild |
| `/root/openarcanum-podman/` | the kit, with your edits |

The timer `openarcanum-site-backup.timer` runs `site backup` daily and keeps
the newest 14. It is safe while the site runs. By hand:

```sh
oa-podman exec openarcanum-site site backup -out /data/backups -keep 14
ls -lt /home/openarcanum/site/data/backups/
oa-systemctl list-timers openarcanum-site-backup.timer
```

Copy them off the machine, for example from your own computer:

```sh
rsync -a root@openarcanum.org:/home/openarcanum/site/data/backups/ ./site-backups/
```

### Restore

```sh
BACKUP=site-backup-20261026T030000.000Z.db     # the file to restore
cd /home/openarcanum/site/data
oa-systemctl stop openarcanum-site
mkdir -p before-restore
mv site.db before-restore/
mv site.db-wal site.db-shm before-restore/ 2>/dev/null || true
install -m 0600 -o openarcanum -g openarcanum backups/"$BACKUP" site.db
oa-systemctl start openarcanum-site
```

`/home/openarcanum/site/keys/storage.key` must be the key the backup was made
with. With another key the site refuses to start and says so. On a rebuilt
server, put your saved copy of the key in place (owner `openarcanum`, mode
0600) before the first start.

### Test a restore

The site keeps running. This opens a copy of the newest backup with a copy of
the key and lists the admins:

```sh
IMAGE=$(sed -n 's/^Image=//p' /home/openarcanum/.config/containers/systemd/openarcanum-site.container)
BACKUP=$(ls -t /home/openarcanum/site/data/backups/ | head -n1)
T=/home/openarcanum/site/restore-test
install -d -m 0700 -o openarcanum -g openarcanum $T $T/data $T/keys
install -m 0600 -o openarcanum -g openarcanum /home/openarcanum/site/data/backups/"$BACKUP" $T/data/site.db
install -m 0600 -o openarcanum -g openarcanum /home/openarcanum/site/keys/storage.key $T/keys/storage.key
oa-podman run --rm --network none --userns=keep-id:uid=65532,gid=65532 \
    -v $T:/t:Z -e OPENARCANUM_SITE_STORAGE_KEY_FILE=/t/keys/storage.key \
    "$IMAGE" admin list -data /t/data
rm -rf $T
```

If it lists the admins, the backup and the key work together.

Never mount the live directories (`data`, `keys`, `acme`, `config`) into a
second container while the site runs. `:Z` gives them that container's SELinux
label and the running site then loses access to them until it restarts.

## Certificates

The site gets its certificate from Let's Encrypt by itself (tls-alpn-01 on port
443) and renews it when two thirds of its lifetime have passed. The account key
and the certificates are kept in `/home/openarcanum/site/acme/`, so restarts
don't ask again. Every answer carries HSTS (two years, without subdomains).

The certificate covers `openarcanum.org` only. To serve `www.openarcanum.org`
too, create its DNS record first, then add it to `tls_domains` in site.json
and run setup.sh. The site answers only the names in `tls_domains`.

See what is served:

```sh
echo | openssl s_client -connect 127.0.0.1:443 -servername openarcanum.org 2>/dev/null \
    | openssl x509 -noout -subject -issuer -dates
journalctl CONTAINER_NAME=openarcanum-site | grep -i 'tls certificate'
```

`tls certificate issued` means it worked. `tls certificate not obtained` comes
with the CA's reason, and the site retries after a minute, then backs off up to
an hour. When it fails, check in this order:

1. DNS: `getent ahosts openarcanum.org` must give this server's public
   address. Check from outside too (`dig +short openarcanum.org`).
2. Port 443 from the internet: from another machine,
   `curl -v https://openarcanum.org/`. Then `firewall-cmd --list-ports` on the
   server, and any cloud firewall or security group.
3. Nothing else on 443: `ss -tlnp 'sport = :443'` must show only `site`.
4. The clock: `timedatectl` must say `System clock synchronized: yes`.
5. Rate limits: Let's Encrypt allows 5 certificates for the same set of names
   per week and 5 failed validations per name per hour. Don't delete the acme
   directory to "start fresh". To experiment, set `"acme_directory_url":
   "https://acme-staging-v02.api.letsencrypt.org/directory"` in site.json,
   run setup.sh, and remove it again when done (staging certificates are not
   trusted, so setup.sh's TLS check fails while it is set).

## Firewall, ports, SELinux

| Port | Why |
|---|---|
| 443/tcp | the website (HTTPS) and the ACME challenge |
| 80/tcp | forwarded by firewalld to 7380, which redirects to https |
| 127.0.0.1:7301/tcp | status listener: `/healthz`, `/metrics`. Loopback only, not opened |

```sh
firewall-cmd --list-all       # ports: 443/tcp, forward-ports: port=80:proto=tcp:toport=7380
sysctl net.ipv4.ip_unprivileged_port_start     # 443
```

The redirect on port 80 can't be tested from the server itself (forwarding
applies to traffic from outside). From another machine:
`curl -I http://openarcanum.org/` must answer with a redirect to https.

The report forms limit reports per client network. That only works because the
site sees real client addresses: it binds 443 itself on the host network. Port
80 goes through a forward, which is fine because it only redirects.

SELinux stays enforcing. The `:Z` option on each mount relabels the directory
with `container_file_t` and a category pair private to this container, every
time the container starts. Check with:

```sh
ls -Zd /home/openarcanum/site/{config,data,keys,acme}
ausearch -m AVC -ts recent
```

Don't use `chcon` on these directories and don't turn SELinux off. If labels
look wrong, restarting the service fixes them.

## Website tasks

### Admin accounts

All of these are safe while the site runs:

```sh
S="oa-podman exec -it openarcanum-site site admin"
$S list                  # names, two-factor on or off, last sign-in, lockouts
$S add NAME              # new admin; asks for a passphrase
$S totp NAME             # turn on two-factor sign-in (strongly recommended)
$S totp NAME -off        # turn it off (lost phone); then turn it on again
$S passwd NAME           # new passphrase; also clears a lockout and ends sessions
$S unlock NAME           # clear a lockout after failed sign-ins
$S remove NAME           # delete the admin and their sessions; their notes stay
```

Five failed sign-ins lock an account for a minute, doubling up to an hour.
`unlock` clears it.

### Announcements and reports

Both are handled in the browser at `https://openarcanum.org/admin`.

- Announcements are written in Markdown and appear on the home page.
- Reports arrive from the forms. Each has a kind (bug or security, security
  marked in red), a status, a severity, an assignee and internal notes. Every
  change is recorded as a note. Spam can be deleted.
- To answer a reporter, copy their user ID from the report, find them in the
  community they named, and message them.

### Settings

Edit `site.json` in the kit and run setup.sh. Useful keys:

| Key | Meaning |
|---|---|
| `contact_community` | the community reporters are asked to be in, so the team can message them |
| `download_url`, `source_url` | links on the landing page |
| `reports_per_hour` | reports per client network per hour [5] |
| `reports_per_day` | reports from everyone per day [500]; raise it if a flood blocks real reports |
| `report_pow_bits` | proof-of-work difficulty of the forms [18] |
| `session_ttl`, `session_idle` | admin sign-in lifetime [12h] and idle timeout [1h] |

The security policy and the landing page text are part of the image
(`internal/site/templates/` in the repository). Changing them means a new
release.

## Troubleshooting

**The service won't start.**

```sh
oa-systemctl status openarcanum-site
journalctl _SYSTEMD_USER_UNIT=openarcanum-site.service -n 50
journalctl CONTAINER_NAME=openarcanum-site -n 50
```

- `Unit openarcanum-site.service not found`: Quadlet did not generate it.
  Run `runuser -u openarcanum -- /usr/libexec/podman/quadlet -dryrun -user` to
  see why (a typo, or a key this podman version doesn't know).
- `invalid config` or `unknown field`: a mistake in site.json. Fix it in the
  kit and run setup.sh.
- `the storage key does not match`: `keys/storage.key` is not the key this
  database was made with. Put the right one back.
- The image can't be pulled (`unauthorized`, `denied`): see "GHCR" in
  `/root/openarcanum-podman/README.md`.
- Nothing starts after a reboot: `loginctl show-user openarcanum -p Linger`
  must say `Linger=yes`.

**Permission denied on /data, /keys or /acme.** Rootless podman and SELinux
both apply here.

```sh
ls -lnd /home/openarcanum/site/{data,keys,acme}   # owner must be openarcanum's uid
id -u openarcanum
ls -Zd /home/openarcanum/site/{data,keys,acme}    # container_file_t
ausearch -m AVC -ts recent
```

- Wrong owner (root, or a large uid like 165531 left by `podman unshare chown`):
  `chown -R openarcanum:openarcanum /home/openarcanum/site/data /home/openarcanum/site/keys /home/openarcanum/site/acme`
  and restart. With `keep-id` the right owner on the host is `openarcanum`
  itself.
- Wrong label (`user_home_t`, or AVC denials): restart the service. `:Z`
  relabels on start. If you mounted the directory into another container,
  that is the cause.
- `/etc/subuid` without an `openarcanum` line: run setup.sh again, then
  `oa-podman system migrate`.

**Port 443 bind refused.** `listen tcp :443: bind: permission denied` means
the sysctl is missing: `sysctl net.ipv4.ip_unprivileged_port_start` must print
443 or less (`sysctl -p /etc/sysctl.d/90-openarcanum.conf`). `address already
in use` means another program has 443: `ss -tlnp 'sport = :443'`.

**ACME fails.** See "Certificates" above.

**421 Misdirected Request.** The site answers only the names in
`tls_domains`. Use `https://openarcanum.org/`, not the IP address.

**Can't sign in.** Check `$S list` for a lockout and `unlock` it. A lost
authenticator: `$S totp NAME -off`, sign in, then turn it on again. Admin
cookies need https, so sign in at `https://openarcanum.org/admin`.

**Clock skew.** TLS checks dates, and two-factor codes are time based. A clock
that is off by more than 30 seconds rejects valid codes.

```sh
timedatectl
chronyc tracking
chronyc sources
systemctl restart chronyd
```
