# maintainer-01.openarcanum.org

This server runs the OpenArcanum maintainer node: the relay registry, DM
mailboxes, DM file blobs and the public community directory
(switched off). Keep this file at /root/README.md on the server.

## The machine

| | |
|---|---|
| Name | maintainer-01.openarcanum.org (DNS A record) |
| Provider | DigitalOcean droplet: 1 vCPU, 1.7 GiB memory, 49 GB disk |
| System | Rocky Linux 10.2, x86_64, SELinux enforcing |
| Addresses | public 164.90.142.140 on `ens3` (which also has 10.17.0.5, DigitalOcean's internal anchor address); `ens4` 10.132.0.2 is the private network |
| Login | root over SSH with the deploy key: `ssh -i ~/.ssh/openarcanum_deploy root@maintainer-01.openarcanum.org` |
| Open to the internet | only 22/tcp (ssh) and 443/tcp (the maintainer node); firewalld zone `public` |
| Installed by setup.sh | podman 5.8.2, firewalld 2.4.3, chrony and cosign 3.1.4 (cosign's RPM from GitHub, checksum pinned in `lib/common.sh`) |

Only sshd and the service set up here listen to the network (`ss -tulnp`
lists them; chronyd's 323/udp is on localhost only). setup.sh closes every
other firewalld service and port, and stops and masks the Cockpit web
console (`cockpit.socket`, 9090/tcp) that the droplet image starts. To get
Cockpit back: `systemctl unmask --now cockpit.socket` and
`firewall-cmd --permanent --add-service=cockpit && firewall-cmd --reload`
(setup.sh closes it again when it runs).

Operating system updates are not automatic: run `dnf upgrade` and reboot
now and then, then check the service ("Start, stop, status, logs").

## What runs here, and as whom

- One container, `openarcanum-maintainer`, from the image
  `ghcr.io/hyperkubeorg/openarcanum-maintainer`. The program inside is `meta`.
- It runs under rootless podman as the user `openarcanum`. That user has no
  password and no sudo. Root manages it.
- systemd starts it at boot. The unit is a systemd **user** unit of
  `openarcanum`, generated by Quadlet from a `.container` file. Lingering is
  on for the user, so its units start without anyone logging in.
- The container uses the host network. It listens on 443/tcp itself and gets
  its own certificate from Let's Encrypt.
- Inside the container the program runs as uid 65532. On the host that uid is
  the user `openarcanum` (`UserNS=keep-id:uid=65532,gid=65532`). So every file
  it writes is owned by `openarcanum`.

Two helper commands, installed by setup.sh, run things as `openarcanum` from a
root shell:

```sh
oa-systemctl status openarcanum-maintainer    # systemctl --user as openarcanum
oa-podman ps                                  # podman as openarcanum
```

| `/home/openarcanum/maintainer/data/backups/` | backups from `meta backup` |

The kit in `/root/openarcanum-podman/maintainer-01.openarcanum.org/` is the
source of truth. To change the config or the image tag, edit the files there
and run `setup.sh` again. It copies them into place and restarts the node only
when something changed. Edits made directly under `/home/openarcanum` are
overwritten the next time setup.sh runs.

## How it was set up

From a checkout of the repository on your own machine:

```sh
scp -r deploy/podman root@maintainer-01.openarcanum.org:/root/openarcanum-podman
ssh root@maintainer-01.openarcanum.org
bash /root/openarcanum-podman/maintainer-01.openarcanum.org/setup.sh
```

Before that, the DNS A record (and AAAA, if the server has IPv6) for
`maintainer-01.openarcanum.org` must point at this server. Let's Encrypt
checks it.

The script stops at the first error and can be run again at any time. It does
this, in order:

1. Installs `podman`, `container-selinux`, `firewalld`, `chrony`, `curl`,
   `openssl`, `rsync` with dnf, cosign from its GitHub release (the rpm's
   checksum is in `lib/common.sh`), and checks podman is 4.9 or newer.
2. Enables chronyd and checks the clock is synchronized.
3. Creates the user `openarcanum`, checks it has 65536 subordinate uids and
   gids (`/etc/subuid`, `/etc/subgid`), and runs
   `loginctl enable-linger openarcanum`.
4. Writes `/etc/sysctl.d/90-openarcanum.conf` with
   `net.ipv4.ip_unprivileged_port_start = 443` and applies it.
5. Opens 443/tcp in firewalld (permanent, then reload).
   Closes every other firewalld service and port (ssh stays), and stops
   and masks Cockpit.
6. Creates `/home/openarcanum/maintainer/{config,data,acme}` owned by
   `openarcanum`, mode 0700 for data and acme.
7. Installs `oa-podman` and `oa-systemctl`.
8. Copies `meta.json`, the Quadlet file, the backup units and this README into
   place, and runs `restorecon` on `~openarcanum/.config`.
9. Runs the Quadlet generator in dry-run mode to catch mistakes.
10. Checks DNS, checks the image's cosign signature and pulls the digest it
    covers, as `openarcanum`.
11. Runs `systemctl --user daemon-reload`, enables the backup timer and
    (re)starts `openarcanum-maintainer`.
12. Checks: the unit is active, the container health check passes, a trusted
    certificate is served for the name, `/v1/relays` answers. Then it prints
    the node key and the directory status.

## Start, stop, status, logs

```sh
oa-systemctl status openarcanum-maintainer
oa-systemctl restart openarcanum-maintainer
oa-systemctl stop openarcanum-maintainer
oa-systemctl start openarcanum-maintainer
```

`enable` and `disable` don't apply to Quadlet units. The `[Install]` section of
the `.container` file makes it start at boot. To keep it from starting at
boot, move the `.container` file out of the Quadlet directory and run
`oa-systemctl daemon-reload`.

Logs go to journald:

```sh
journalctl CONTAINER_NAME=openarcanum-maintainer -f            # the node's own log
journalctl CONTAINER_NAME=openarcanum-maintainer --since today
journalctl _SYSTEMD_USER_UNIT=openarcanum-maintainer.service   # start/stop messages too
oa-podman healthcheck run openarcanum-maintainer && echo healthy
```

Logs never hold message content, keys, tokens or client addresses. Journald
keeps them within its own size limits (`SystemMaxUse=` in
`/etc/systemd/journald.conf`).

Metrics and health on the status listener (loopback only):

```sh
curl -s http://127.0.0.1:7100/healthz
curl -s http://127.0.0.1:7100/metrics | grep '^openarcanum_meta_'
```

## Updating to a new release, and rolling back

The image tag is pinned in the Quadlet file (`Image=...:2026.10.4`). Releases
are tagged `<version>` (for example `2026.10.1`), `YYYY.MM` and `latest`.
setup.sh takes a tag only with a valid cosign signature made by the
repository's Containers workflow for a release tag, and pulls the digest that
signature covers (it prints it). To pin that digest as well, append it to
the tag: `Image=...:2026.10.4@sha256:<digest>`.

To upgrade:

```sh
# 1. Take a backup first. Rolling back needs it.
oa-podman exec openarcanum-maintainer meta backup -data /data -out /data/backups -keep 7
# 2. Change the tag in the kit.
cd /root/openarcanum-podman/maintainer-01.openarcanum.org
sed -i 's|^Image=.*|Image=ghcr.io/hyperkubeorg/openarcanum-maintainer:2026.10.1|' openarcanum-maintainer.container
# 3. Pull, restart, check.
bash setup.sh
```

The node migrates its database on start. An older release refuses a database
written by a newer one. So rolling back means the old tag plus the backup
taken before the upgrade:

```sh
cd /root/openarcanum-podman/maintainer-01.openarcanum.org
sed -i 's|^Image=.*|Image=ghcr.io/hyperkubeorg/openarcanum-maintainer:2026.10.0|' openarcanum-maintainer.container
bash setup.sh        # will fail its checks if the schema is newer; then restore:
```

and restore that backup as described below. If the new release did not change
the schema, the old tag alone is enough.

### Automatic updates

The container carries the label `io.containers.autoupdate=registry`.
`podman auto-update` pulls the pinned tag again and restarts the node when the
tag points at a new image. With a version tag that only happens if a release is
republished. To follow fixes for the month automatically, set the tag to
`YYYY.MM` (for example `2026.10`).

The timer that runs it daily is off, and `podman auto-update` pulls without
the signature check setup.sh does, so changing the tag and running setup.sh
is the better way. To check or turn it on anyway:

```sh
oa-podman auto-update --dry-run
oa-systemctl enable --now podman-auto-update.timer
oa-systemctl list-timers
```

If the new container fails to start, podman rolls back to the previous image.
It does not take a backup first. Keep the daily backups if you turn this on.

## Backups and restore

What to keep:

| Path | Why |
|---|---|
| `/home/openarcanum/maintainer/data/backups/meta-*.tar` | the database and the DM blobs, consistent, from `meta backup` |
| `/home/openarcanum/maintainer/acme/` | optional: saves asking Let's Encrypt again after a restore |
| `/root/openarcanum-podman/` | the kit, with your edits |

The node keys (`node.key`, `node.noise`) are not in the backup; a node
restored without them makes new ones at its first start. That only matters
once this node is in a maintainer cluster (the member list names its key). To
keep them, copy `data/node.key` and `data/node.noise` off the machine as well.
A backup holds what the data directory holds otherwise: ciphertext, signed
public records, inbox addresses, sizes and times. Treat it as private.

The timer `openarcanum-maintainer-backup.timer` runs `meta backup` daily and
keeps the newest 7. It is safe while the node runs. By hand:

```sh
oa-podman exec openarcanum-maintainer meta backup -data /data -out /data/backups -keep 7
ls -lt /home/openarcanum/maintainer/data/backups/
oa-systemctl list-timers openarcanum-maintainer-backup.timer
journalctl _SYSTEMD_USER_UNIT=openarcanum-maintainer-backup.service -n 20
```

Copy them off the machine, for example from your own computer:

```sh
rsync -a root@maintainer-01.openarcanum.org:/home/openarcanum/maintainer/data/backups/ ./maintainer-01-backups/
```

### Copying backups to another machine

`openarcanum-maintainer-backup-sync.service` runs after each backup and
rsyncs `data/backups/` over SSH to a place you name. It does nothing until
`/home/openarcanum/maintainer/backup-remote/env` exists:

```sh
D=/home/openarcanum/maintainer/backup-remote
install -d -m 0700 -o openarcanum -g openarcanum $D
ssh-keygen -t ed25519 -N '' -C maintainer-01-backups -f $D/ssh.key
ssh-keyscan backup.example.org > $D/known_hosts
echo 'BACKUP_REMOTE=backup@backup.example.org:/srv/openarcanum/maintainer-01' > $D/env
chown openarcanum:openarcanum $D/*
chmod 0600 $D/*
oa-systemctl start openarcanum-maintainer-backup-sync     # try it once
journalctl _SYSTEMD_USER_UNIT=openarcanum-maintainer-backup-sync.service -n 20
```

On the other machine, give `ssh.key.pub` a line in that user's
`authorized_keys` that allows nothing but writing into the directory:

```
restrict,command="rrsync -wo /srv/openarcanum/maintainer-01" ssh-ed25519 AAAA... maintainer-01-backups
```

(`rrsync` comes with rsync.) Nothing is deleted there: the copies pile up
until you prune them, while this machine keeps the newest 7. The key can only
add files to that directory, so a break-in here can't read or wipe the
copies. To stop copying, delete `env`.

### Restore

`meta restore` needs an empty data directory. Run it with the same release
that runs the node (or a newer one).

```sh
IMAGE=$(sed -n 's/^Image=//p' /home/openarcanum/.config/containers/systemd/openarcanum-maintainer.container)
BACKUP=meta-20261026T030000.000Z.tar     # the file to restore
cd /home/openarcanum/maintainer
oa-systemctl stop openarcanum-maintainer
mv data data.before-restore
install -d -m 0700 -o openarcanum -g openarcanum data restore-from
install -m 0600 -o openarcanum -g openarcanum data.before-restore/backups/"$BACKUP" restore-from/
oa-podman run --rm --network none --userns=keep-id:uid=65532,gid=65532 \
    -v /home/openarcanum/maintainer/data:/data:Z \
    -v /home/openarcanum/maintainer/restore-from:/restore-from:ro,Z \
    "$IMAGE" restore -data /data -backup /restore-from/"$BACKUP"
mv data.before-restore/backups data/
cp -p data.before-restore/node.key data.before-restore/node.noise data/   # keep the node's identity
oa-systemctl start openarcanum-maintainer
```

When the node is healthy again, delete `restore-from` and, once you are sure,
`data.before-restore`. A restore that fails leaves `data` as it was, so it can
be run again.

### Test a restore

Do this every few months, and after upgrades. The node keeps running.

```sh
IMAGE=$(sed -n 's/^Image=//p' /home/openarcanum/.config/containers/systemd/openarcanum-maintainer.container)
BACKUP=$(ls -t /home/openarcanum/maintainer/data/backups/ | head -n1)
T=/home/openarcanum/maintainer/restore-test
install -d -m 0700 -o openarcanum -g openarcanum $T $T/data $T/from
install -m 0600 -o openarcanum -g openarcanum /home/openarcanum/maintainer/data/backups/"$BACKUP" $T/from/
oa-podman run --rm --network none --userns=keep-id:uid=65532,gid=65532 \
    -v $T:/t:Z "$IMAGE" restore -data /t/data -backup /t/from/"$BACKUP"
oa-podman run --rm --network none --userns=keep-id:uid=65532,gid=65532 \
    -v $T:/t:Z "$IMAGE" relays list -data /t/data
rm -rf $T
```

`restore` checks every file against the backup's manifest and opens the
restored database once. If both commands succeed, the backup is good.

Never mount the live directories (`data`, `acme`, `config`) into a second
container while the node runs. `:Z` gives them that container's SELinux label
and the running node then loses access to them until it restarts.

## Certificates

The node gets its certificate from Let's Encrypt by itself (tls-alpn-01 on port
443, no port 80 needed) and renews it when two thirds of its lifetime have
passed. The account key and the certificates are kept in
`/home/openarcanum/maintainer/acme/`, so restarts don't ask again.

See what is served:

```sh
echo | openssl s_client -connect 127.0.0.1:443 -servername maintainer-01.openarcanum.org 2>/dev/null \
    | openssl x509 -noout -subject -issuer -dates
journalctl CONTAINER_NAME=openarcanum-maintainer | grep -i 'tls certificate'
```

`tls certificate issued` means it worked. `tls certificate not obtained` comes
with the CA's reason, and the node retries after a minute, then backs off up to
an hour. When it fails, check in this order:

1. DNS: `getent ahosts maintainer-01.openarcanum.org` must give this server's
   public address. Check from outside too (`dig +short maintainer-01.openarcanum.org`).
2. Port 443 from the internet: from another machine,
   `curl -v https://maintainer-01.openarcanum.org/healthz`. Then
   `firewall-cmd --list-ports` on the server, and any cloud firewall or
   security group.
3. Nothing else on 443: `ss -tlnp 'sport = :443'` must show only `meta`.
4. The clock: `timedatectl` must say `System clock synchronized: yes`.
5. Rate limits: Let's Encrypt allows 5 certificates for the same name per week
   and 5 failed validations per name per hour. Don't delete the acme directory
   to "start fresh". To experiment, set `"acme_directory_url":
   "https://acme-staging-v02.api.letsencrypt.org/directory"` in meta.json,
   run setup.sh, and remove it again when done (staging certificates are not
   trusted, so setup.sh's TLS check fails while it is set).

## Firewall, ports, SELinux

| Port | Why |
|---|---|
| 443/tcp | the API (HTTPS) and the ACME challenge |
| 127.0.0.1:7100/tcp | status listener: `/healthz`, `/metrics`. Loopback only, not opened |

```sh
firewall-cmd --list-all
sysctl net.ipv4.ip_unprivileged_port_start     # 443
```

SELinux stays enforcing. The `:Z` option on each mount relabels the directory
with `container_file_t` and a category pair private to this container, every
time the container starts. Check with:

```sh
ls -Zd /home/openarcanum/maintainer/{config,data,acme}
ausearch -m AVC -ts recent
```

Don't use `chcon` on these directories and don't turn SELinux off. If labels
look wrong, restarting the service fixes them.

## Maintainer tasks

All admin commands run inside the running container against `/data`, and are
safe while the node runs:

```sh
M="oa-podman exec openarcanum-maintainer meta"
$M id -data /data                       # this node's public node key
$M relays list -data /data              # the relay registry as stored
$M relays remove -data /data -url wss://bad-relay.example/ws -reason "abuse"
$M relays restore -data /data -url wss://bad-relay.example/ws
$M directory status -data /data -config /etc/openarcanum/meta.json
$M directory list -data /data -q TEXT
$M directory delist -data /data -id COMMUNITY_ID -reason "why"
$M directory relist -data /data -id COMMUNITY_ID
$M directory decisions -data /data -config /etc/openarcanum/meta.json
$M peers status -data /data             # maintainer cluster peers (none yet)
$M blobs stats -data /data
```

Reasons stay on this node. They are for your records.

Relays that registered, as clients see them:

```sh
curl -s -H 'OpenArcanum-Protocol: 1' https://maintainer-01.openarcanum.org/v1/relays | grep -ao 'wss://[a-z0-9.:/-]*'
```

### Enabling the public directory later

The directory is off (`"directory_enabled": false`). Communities are joined
through invites. To run a public community list:

```sh
cd /root/openarcanum-podman/maintainer-01.openarcanum.org
sed -i 's/"directory_enabled": false/"directory_enabled": true/' meta.json
bash setup.sh
oa-podman exec openarcanum-maintainer meta directory status -data /data -config /etc/openarcanum/meta.json
```

Communities appear with their next publication (within about 10 minutes). To
take it down quickly, `meta directory disable -data /data` works on the
running node and deletes every listing; set the config back to `false` as well.

### Relay settings that matter here

`"relay_proof": true` lists a relay only after this node fetched the relay's
public URL and got the relay's key back. `"allow_private_relays": false`
refuses relays on private addresses. Keep both as they are in production.

## Troubleshooting

**The service won't start.**

```sh
oa-systemctl status openarcanum-maintainer
journalctl _SYSTEMD_USER_UNIT=openarcanum-maintainer.service -n 50
journalctl CONTAINER_NAME=openarcanum-maintainer -n 50
```

- `Unit openarcanum-maintainer.service not found`: Quadlet did not generate it.
  Run `runuser -u openarcanum -- /usr/libexec/podman/quadlet -dryrun -user` to
  see why (a typo, or a key this podman version doesn't know).
- `invalid config` or `unknown field`: a mistake in meta.json. Fix it in the
  kit and run setup.sh.
- The image can't be pulled (`unauthorized`, `denied`): see "GHCR" in
  `/root/openarcanum-podman/README.md`.
- `no valid signature`: the tag isn't a release (branch and `sha-<commit>`
  images are signed for other refs), or the package is private and cosign
  has no login (see "GHCR" there).
- Nothing starts after a reboot: `loginctl show-user openarcanum -p Linger`
  must say `Linger=yes`.

**Permission denied on /data or /acme.** Rootless podman and SELinux both
apply here.

```sh
ls -lnd /home/openarcanum/maintainer/{data,acme}   # owner must be openarcanum's uid
id -u openarcanum
ls -Zd /home/openarcanum/maintainer/{data,acme}    # container_file_t
ausearch -m AVC -ts recent
```

- Wrong owner (root, or a large uid like 165531 left by `podman unshare chown`):
  `chown -R openarcanum:openarcanum /home/openarcanum/maintainer/data /home/openarcanum/maintainer/acme`
  and restart. With `keep-id` the right owner on the host is `openarcanum`
  itself.
- Wrong label (`user_home_t`, or AVC denials): restart the service. `:Z`
  relabels on start. If you mounted the directory into another container,
  that is the cause.
- `/etc/subuid` without an `openarcanum` line: run setup.sh again, then
  `oa-podman system migrate`.

**Port 443 bind refused.** `listen tcp :443: bind: permission denied` means
the sysctl is missing: `sysctl net.ipv4.ip_unprivileged_port_start` must print
443 or less (`sysctl -p /etc/sysctl.d/90-openarcanum.conf`). `address already
in use` means another program has 443: `ss -tlnp 'sport = :443'`.

**ACME fails.** See "Certificates" above.

**A relay is not listed.** On this node:

```sh
journalctl CONTAINER_NAME=openarcanum-maintainer --since -15min | grep -i relay
oa-podman exec openarcanum-maintainer meta relays list -data /data
oa-podman exec openarcanum-maintainer meta directory decisions -data /data -config /etc/openarcanum/meta.json
```

The node lists a relay only when a GET of the relay's public URL, from this
server, returns the relay's key. So this server must reach
`https://relay-01.openarcanum.org/ws` (`curl -sv https://relay-01.openarcanum.org/healthz`
from here), with a valid certificate, on a public address. Entries expire 2
minutes after the last heartbeat. A removed relay host stays removed until
`meta relays restore`.

**Clock skew.** Signed heartbeats and records carry times, and TLS checks
dates. A clock that is off by minutes breaks both.

```sh
timedatectl
chronyc tracking
chronyc sources
systemctl restart chronyd
```
