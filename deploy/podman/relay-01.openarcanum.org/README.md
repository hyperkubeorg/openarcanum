# relay-01.openarcanum.org

This server runs an OpenArcanum relay. Clients and community servers connect to
it over WebSocket (`wss://relay-01.openarcanum.org/ws`) and it carries call
media over UDP. It registers with the maintainer node
`https://maintainer-01.openarcanum.org`. Keep this file at /root/README.md on
the server.

## What runs here, and as whom

- One container, `openarcanum-relay`, from the image
  `ghcr.io/hyperkubeorg/openarcanum-relay`. The program inside is `relay`.
- It runs under rootless podman as the user `openarcanum`. That user has no
  password and no sudo. Root manages it.
- systemd starts it at boot. The unit is a systemd **user** unit of
  `openarcanum`, generated by Quadlet from a `.container` file. Lingering is
  on for the user, so its units start without anyone logging in.
- The container uses the host network. It listens on 443/tcp (WebSocket over
  TLS, with its own Let's Encrypt certificate) and 7000/udp (call media).
- Inside the container the program runs as uid 65532. On the host that uid is
  the user `openarcanum` (`UserNS=keep-id:uid=65532,gid=65532`). So every file
  it writes is owned by `openarcanum`.
- The relay is stateless. It stores only its registry key and its
  certificates.

Two helper commands, installed by setup.sh, run things as `openarcanum` from a
root shell:

```sh
oa-systemctl status openarcanum-relay    # systemctl --user as openarcanum
oa-podman ps                             # podman as openarcanum
```

## Where everything lives

| Path | What |
|---|---|
| `/home/openarcanum/.config/containers/systemd/openarcanum-relay.container` | Quadlet file: image tag, mounts, health check |
| `/home/openarcanum/relay/config/relay.json` | relay config, mounted read-only at `/etc/openarcanum/relay.json` |
| `/home/openarcanum/relay/keys/registry.key` | the relay's identity key for heartbeats; mounted at `/keys` |
| `/home/openarcanum/relay/acme/` | Let's Encrypt account key and certificates; mounted at `/acme` |
| `/home/openarcanum/.local/share/containers/` | podman's image store for the user |
| `/etc/sysctl.d/90-openarcanum.conf` | lets unprivileged processes bind port 443 |
| `/usr/local/sbin/oa-podman`, `/usr/local/sbin/oa-systemctl` | the helper commands |
| `/root/openarcanum-podman/` | the setup kit (a copy of `deploy/podman` from the repository) |

The kit in `/root/openarcanum-podman/relay-01.openarcanum.org/` is the source
of truth. To change the config or the image tag, edit the files there and run
`setup.sh` again. It copies them into place and restarts the relay only when
something changed. Edits made directly under `/home/openarcanum` are
overwritten the next time setup.sh runs.

## How it was set up

Set up the maintainer node first. Then, from a checkout of the repository on
your own machine:

```sh
scp -r deploy/podman root@relay-01.openarcanum.org:/root/openarcanum-podman
ssh root@relay-01.openarcanum.org
bash /root/openarcanum-podman/relay-01.openarcanum.org/setup.sh
```

Before that, the DNS A record (and AAAA, if the server has IPv6) for
`relay-01.openarcanum.org` must point at this server.

The script stops at the first error and can be run again at any time. It does
this, in order:

1. Installs `podman`, `container-selinux`, `firewalld`, `chrony`, `curl`,
   `openssl`, `rsync` with dnf, cosign from its GitHub release (the rpm's
   checksum is in `lib/common.sh`), and checks podman is 4.9 or newer.
2. Enables chronyd and checks the clock is synchronized.
3. Creates the user `openarcanum`, checks it has 65536 subordinate uids and
   gids (`/etc/subuid`, `/etc/subgid`), and runs
   `loginctl enable-linger openarcanum`.
4. Writes `/etc/sysctl.d/90-openarcanum.conf` with
   `net.ipv4.ip_unprivileged_port_start = 443` and applies it.
5. Opens 443/tcp and 7000/udp in firewalld (permanent, then reload).
6. Creates `/home/openarcanum/relay/{config,keys,acme}` owned by
   `openarcanum`, mode 0700 for keys and acme.
7. Installs `oa-podman` and `oa-systemctl`.
8. Copies `relay.json`, the Quadlet file and this README into place, and runs
   `restorecon` on `~openarcanum/.config`.
9. Runs the Quadlet generator in dry-run mode to catch mistakes.
10. Checks DNS (and warns when the name points at an address that is not on
    this machine, see "Calls behind NAT"), checks the maintainer node
    answers, then checks the image's cosign signature and pulls the digest
    it covers, as `openarcanum`.
11. Runs `systemctl --user daemon-reload` and (re)starts `openarcanum-relay`.
12. Checks: the unit is active, the container health check passes, a trusted
    certificate is served for the name, and the relay shows up at
    `https://maintainer-01.openarcanum.org/v1/relays`.

## Start, stop, status, logs

```sh
oa-systemctl status openarcanum-relay
oa-systemctl restart openarcanum-relay
oa-systemctl stop openarcanum-relay
oa-systemctl start openarcanum-relay
```

`enable` and `disable` don't apply to Quadlet units. The `[Install]` section of
the `.container` file makes it start at boot. To keep it from starting at
boot, move the `.container` file out of the Quadlet directory and run
`oa-systemctl daemon-reload`.

A restart drops every connection. Clients and community servers reconnect by
themselves within seconds. Calls in progress are interrupted.

Logs go to journald:

```sh
journalctl CONTAINER_NAME=openarcanum-relay -f            # the relay's own log
journalctl CONTAINER_NAME=openarcanum-relay --since today
journalctl _SYSTEMD_USER_UNIT=openarcanum-relay.service   # start/stop messages too
oa-podman healthcheck run openarcanum-relay && echo healthy
```

Logs never hold message content, keys or client addresses.

Metrics and health on the status listener (loopback only, TCP 7000; the media
port is UDP 7000, no conflict):

```sh
curl -s http://127.0.0.1:7000/healthz
curl -s http://127.0.0.1:7000/metrics | grep '^openarcanum_relay_'
```

`openarcanum_relay_connections`, `openarcanum_relay_calls` and
`openarcanum_relay_connections_refused_total` show the load.

## Updating to a new release, and rolling back

The image tag is pinned in the Quadlet file (`Image=...:2026.10.0`). Releases
are tagged `<version>` (for example `2026.10.1`), `YYYY.MM` and `latest`.
setup.sh takes a tag only with a valid cosign signature made by the
repository's Containers workflow for a release tag, and pulls the digest that
signature covers (it prints it). To pin that digest as well, append it to
the tag: `Image=...:2026.10.0@sha256:<digest>`.

To upgrade:

```sh
cd /root/openarcanum-podman/relay-01.openarcanum.org
sed -i 's|^Image=.*|Image=ghcr.io/hyperkubeorg/openarcanum-relay:2026.10.1|' openarcanum-relay.container
bash setup.sh
```

The script pulls the new image before restarting, so the relay is down only for
the restart. To roll back, put the old tag back the same way and run setup.sh.
The relay has no database, so rolling back needs nothing else.

### Automatic updates

The container carries the label `io.containers.autoupdate=registry`.
`podman auto-update` pulls the pinned tag again and restarts the relay when the
tag points at a new image. With a version tag that only happens if a release is
republished. To follow fixes for the month automatically, set the tag to
`YYYY.MM` (for example `2026.10`).

The timer that runs it daily is off, and `podman auto-update` pulls without
the signature check setup.sh does, so changing the tag and running setup.sh
is the better way. To check or turn it on anyway:

```sh
oa-podman auto-update --dry-run
oa-systemctl enable --now podman-auto-update.timer
oa-systemctl list-timers
```

If the new container fails to start, podman rolls back to the previous image.

## Backups and restore

The relay keeps nothing that can't be recreated. Optional:

| Path | Why |
|---|---|
| `/home/openarcanum/relay/acme/` | saves asking Let's Encrypt again on a rebuild (rate limits) |
| `/home/openarcanum/relay/keys/registry.key` | keeps the relay's identity; a new key works too, the maintainer accepts it with the next heartbeat |
| `/root/openarcanum-podman/` | the kit, with your edits |

```sh
tar -C /home/openarcanum/relay -czf /root/relay-01-state.tar.gz keys acme
```

To restore on a rebuilt server, run setup.sh once, then:

```sh
oa-systemctl stop openarcanum-relay
tar -C /home/openarcanum/relay -xzf /root/relay-01-state.tar.gz
chown -R openarcanum:openarcanum /home/openarcanum/relay/keys /home/openarcanum/relay/acme
oa-systemctl start openarcanum-relay
```

To test it, unpack the archive into a scratch directory and check the files are
there: `tar -tzf /root/relay-01-state.tar.gz`.

## Certificates

The relay gets its certificate from Let's Encrypt by itself (tls-alpn-01 on
port 443, no port 80 needed) and renews it when two thirds of its lifetime have
passed. The account key and the certificates are kept in
`/home/openarcanum/relay/acme/`, so restarts don't ask again.

See what is served:

```sh
echo | openssl s_client -connect 127.0.0.1:443 -servername relay-01.openarcanum.org 2>/dev/null \
    | openssl x509 -noout -subject -issuer -dates
journalctl CONTAINER_NAME=openarcanum-relay | grep -i 'tls certificate'
```

`tls certificate issued` means it worked. `tls certificate not obtained` comes
with the CA's reason, and the relay retries after a minute, then backs off up
to an hour. When it fails, check in this order:

1. DNS: `getent ahosts relay-01.openarcanum.org` must give this server's
   public address. Check from outside too (`dig +short relay-01.openarcanum.org`).
2. Port 443 from the internet: from another machine,
   `curl -v https://relay-01.openarcanum.org/healthz`. Then
   `firewall-cmd --list-ports` on the server, and any cloud firewall or
   security group.
3. Nothing else on 443: `ss -tlnp 'sport = :443'` must show only `relay`.
4. The clock: `timedatectl` must say `System clock synchronized: yes`.
5. Rate limits: Let's Encrypt allows 5 certificates for the same name per week
   and 5 failed validations per name per hour. Don't delete the acme directory
   to "start fresh". To experiment, set `"acme_directory_url":
   "https://acme-staging-v02.api.letsencrypt.org/directory"` in relay.json,
   run setup.sh, and remove it again when done (staging certificates are not
   trusted, so setup.sh's TLS check fails while it is set).

## Firewall, ports, SELinux

| Port | Why |
|---|---|
| 443/tcp | WebSocket (`wss://.../ws`), `/healthz`, the ACME challenge |
| 7000/udp | call media (WebRTC, encrypted with DTLS-SRTP) |
| 127.0.0.1:7000/tcp | status listener: `/healthz`, `/metrics`. Loopback only, not opened |

```sh
firewall-cmd --list-all
sysctl net.ipv4.ip_unprivileged_port_start     # 443
```

The relay limits connections per client network. That only works because it
sees real client addresses: it binds 443 itself on the host network. Don't put
a port forward or proxy in front of it without raising the per-network limits.

SELinux stays enforcing. The `:Z` option on each mount relabels the directory
with `container_file_t` and a category pair private to this container, every
time the container starts. Check with:

```sh
ls -Zd /home/openarcanum/relay/{config,keys,acme}
ausearch -m AVC -ts recent
```

Don't use `chcon` on these directories and don't turn SELinux off. If labels
look wrong, restarting the service fixes them.

## Relay tasks

### Checking registration

```sh
curl -s -H 'OpenArcanum-Protocol: 1' https://maintainer-01.openarcanum.org/v1/relays | grep -ao 'wss://[a-z0-9.:/-]*'
```

`wss://relay-01.openarcanum.org/ws` must be in the list. The relay sends a
heartbeat every 30 seconds; the maintainer drops it 2 minutes after the last
one. On the maintainer server,
`oa-podman exec openarcanum-maintainer meta relays list -data /data` shows the
stored entry with its capacity and connection count.

### Capacity

Edit `relay.json` in the kit and run setup.sh. The settings that matter most
(defaults in brackets):

| Key | Meaning |
|---|---|
| `max_connections` | connections in all [10000]; each takes file descriptors and memory |
| `max_connections_per_ip` | connections from one IPv4 address or IPv6 /64 [256] |
| `bytes_per_second`, `byte_burst` | bandwidth per connection [16 MiB/s, 32 MiB] |
| `max_calls` | calls at once [1000] |
| `max_call_peers` | call participants in all [5000] |
| `max_call_peers_per_ip` | call participants from one network [20] |
| `call_peer_bitrate` | bits per second one participant may send [8000000] |
| `chunk_cache_bytes` | memory for the optional message cache [0, off] |
| `pow_mode`, `pow_bits` | proof-of-work for new connections [`load`, 18]; `always` during a connection flood |

The container's open-file limit is 65536 (`Ulimit=` in the Quadlet file). Keep
`max_connections` well below it.

### Turning calls off

Set `"calls": false` in relay.json and run setup.sh. The relay then tells
clients it carries no calls. You can also close the media port:

```sh
firewall-cmd --permanent --remove-port=7000/udp && firewall-cmd --reload
```

(setup.sh opens it again the next time it runs; remove `7000/udp` from
`UDP_PORTS` in setup.sh to keep it closed.)

### Calls behind NAT

If this server's public address is not on one of its interfaces (some cloud
providers use 1:1 NAT), the relay would offer its private address for media.
Put the public address in relay.json and run setup.sh:

```json
"media_public_ips": ["203.0.113.7"]
```

`ip -brief addr` shows the interface addresses. If the public address is there,
leave the list empty.

## Troubleshooting

**The service won't start.**

```sh
oa-systemctl status openarcanum-relay
journalctl _SYSTEMD_USER_UNIT=openarcanum-relay.service -n 50
journalctl CONTAINER_NAME=openarcanum-relay -n 50
```

- `Unit openarcanum-relay.service not found`: Quadlet did not generate it.
  Run `runuser -u openarcanum -- /usr/libexec/podman/quadlet -dryrun -user` to
  see why (a typo, or a key this podman version doesn't know).
- `invalid config` or `unknown field`: a mistake in relay.json. Fix it in the
  kit and run setup.sh.
- The image can't be pulled (`unauthorized`, `denied`): see "GHCR" in
  `/root/openarcanum-podman/README.md`.
- `no valid signature`: the tag isn't a release (branch and `sha-<commit>`
  images are signed for other refs), or the package is private and cosign
  has no login (see "GHCR" there).
- Nothing starts after a reboot: `loginctl show-user openarcanum -p Linger`
  must say `Linger=yes`.

**Permission denied on /keys or /acme.** Rootless podman and SELinux both
apply here.

```sh
ls -lnd /home/openarcanum/relay/{keys,acme}   # owner must be openarcanum's uid
id -u openarcanum
ls -Zd /home/openarcanum/relay/{keys,acme}    # container_file_t
ausearch -m AVC -ts recent
```

- Wrong owner (root, or a large uid like 165531 left by `podman unshare chown`):
  `chown -R openarcanum:openarcanum /home/openarcanum/relay/keys /home/openarcanum/relay/acme`
  and restart. With `keep-id` the right owner on the host is `openarcanum`
  itself.
- Wrong label (`user_home_t`, or AVC denials): restart the service. `:Z`
  relabels on start. If you mounted the directory into another container,
  that is the cause.
- `/etc/subuid` without an `openarcanum` line: run setup.sh again, then
  `oa-podman system migrate`.

**Port 443 bind refused.** `listen tcp :443: bind: permission denied` means
the sysctl is missing: `sysctl net.ipv4.ip_unprivileged_port_start` must print
443 or less (`sysctl -p /etc/sysctl.d/90-openarcanum.conf`). `address already
in use` means another program has 443: `ss -tlnp 'sport = :443'`.

**ACME fails.** See "Certificates" above.

**The relay is not listed at the maintainer.** In order:

1. The relay's log: `journalctl CONTAINER_NAME=openarcanum-relay --since -10min | grep -i -e heartbeat -e registry`.
   Errors there name the maintainer's answer.
2. The maintainer answers from here:
   `curl -s https://maintainer-01.openarcanum.org/healthz`.
3. Proof of control. The maintainer lists the relay only after it fetched
   `https://relay-01.openarcanum.org/ws` itself and got the relay's key back.
   So the relay must be reachable from the maintainer server at its public
   name, on a public address, with a trusted certificate. On the maintainer
   server: `curl -sv https://relay-01.openarcanum.org/healthz`.
4. `public_url` in relay.json must be exactly `wss://relay-01.openarcanum.org/ws`.
5. The relay host was not removed at the maintainer:
   `oa-podman exec openarcanum-maintainer meta directory decisions -data /data`
   on the maintainer server.
6. Clocks on both servers (below).

**Calls connect but no audio or video.** 7000/udp must reach the server: check
`firewall-cmd --list-ports`, the cloud firewall, and "Calls behind NAT".

**Clock skew.** Heartbeats are signed with a time, and TLS checks dates. A clock
that is off by minutes breaks both.

```sh
timedatectl
chronyc tracking
chronyc sources
systemctl restart chronyd
```
